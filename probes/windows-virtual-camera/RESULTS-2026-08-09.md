## Frame-server process and session (ADR 0006)

DebugView 5.02 was run elevated with Global Win32 capture. The probe's
`DllMain` recorded both the process id and `ProcessIdToSessionId` result.

| Activation | PID | Session |
|---|---:|---:|
| Validation host | 4436 | 1 |
| Windows frame server (`svchost.exe`) | 4352 | 0 |

**Conclusion:** the MF source runs in session 0, not the interactive user's
session. A `Local\` mapping created by the user app is therefore not visible
to the source. The current bridge name is not viable for this process layout;
`Global\` plus suitable security or a broker-owned mapping must be measured
before choosing the runtime design.

## Anything surprising

- `MFCreateVirtualCamera` itself succeeds with HKCU-only registration; failure
  is delayed until `IMFVirtualCamera::Start`, when the frame server attempts
  activation.
- The source is loaded once in the calling host during validation (session 1)
  and again in the actual Windows frame server (session 0).
- A source that allocates arbitrary `MFCreateMemoryBuffer` samples can work
  under a direct Source Reader but stall in the frame-server path. The source
  now advertises `MFSampleAllocatorUsage_UsesProvidedAllocator` and uses the
  allocator supplied through `IMFSampleAllocatorControl`, matching the Windows
  camera sample contract.
- The product source passed both direct COM activation and delivery through the
  actual frame-server proxy. Temporary lifecycle tracing showed that the first
  failed proxy run was not an activation or allocator failure: the source was
  queueing frames, but their zero-based timestamps made them stale relative to
  the Media Foundation clock. Using `MFGetSystemTime()` made the bounded proxy
  test return the first complete frame in under one second.
